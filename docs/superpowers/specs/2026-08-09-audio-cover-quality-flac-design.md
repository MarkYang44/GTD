# 音频封面、质量标识与源 FLAC 下载设计

## 目标

在现有独立音频下载流程中增加三项能力：将视频封面嵌入音频文件、在文件名末尾标注真实的成品质量与源音轨信息，并允许用户在 MP3 V0 与源 FLAC 之间选择。功能同时覆盖 Web 与命令行入口，保持现有视频下载、批量队列和并发行为不变。

## 已验证现状

- 当前音频配置使用 `bestaudio/best` 选择最高可用源音轨，再由 `FFmpegExtractAudio` 以 `preferredcodec=mp3`、`preferredquality=0` 输出 MP3 V0。
- 当前后处理链没有下载或嵌入缩略图，因此 MP3 播放时显示播放器默认图标。
- Bilibili 适配器已经把 DASH `flac.audio` 纳入格式集合，yt-dlp 的 `bestaudio` 可以选择它。
- 对示例 `BV1fsTM6CE9P` 的真实只读探测选中了格式 `30251`，源编码为 FLAC，约 `1521 kbps`，估算大小约 `783 MB`；该视频同时提供约 66、143、246 kbps 的 AAC 音轨。
- 现有 MP3 流程虽然已经使用该最高质量 FLAC 作为转码源，但 MP3 V0 成品仍是有损音频，不能称为无损或 Hi-Res 文件。

## 产品行为

### 音频格式选择

- 新增独立的 `audio_format` 参数，允许值为 `mp3` 和 `flac`。
- `mp3` 是默认值。未传递新参数的现有调用继续输出 MP3 V0。
- 用户选择 `flac` 时，程序只在源站实际提供 FLAC 编码音轨时输出 `.flac`。
- FLAC 输出采用无损流复制或无损容器提取，不把 FLAC 重新压缩，也不把 AAC、Opus 等有损音轨转码成伪无损 FLAC。
- 如果源站没有 FLAC，程序自动回退到 MP3 V0。CLI、Web 任务卡和下载结果必须明确显示“源站未提供 FLAC，已自动回退至 MP3 V0”。
- YouTube、Instagram 和 Bilibili 共用该规则。平台未来若暴露真实 FLAC 音轨即可使用；否则执行相同回退。

### 封面嵌入

- MP3 和 FLAC 均优先使用视频缩略图作为内嵌封面。
- 后处理顺序为：下载音轨，转换或无损提取，写入元数据，嵌入封面。
- 视频没有缩略图时跳过封面处理，音频任务仍正常完成，结果与现有无封面行为一致。
- 嵌入完成后删除临时缩略图，不在 `downloads/` 留下额外 `.jpg`、`.png` 或 `.webp` 文件。

### 文件命名

质量标签追加在原有基础文件名末尾、扩展名前面。继续保持现有平台命名边界：YouTube 使用标题，Instagram 与 Bilibili 保留 `[内容ID]`。

- MP3，源为 FLAC：`标题 [ID] [MP3 V0 · 源FLAC 1521kbps].mp3`
- MP3，源为 AAC 或 Opus：`标题 [ID] [MP3 V0 · 源AAC 246kbps].mp3`
- 用户选择 FLAC 且源站提供 FLAC：`标题 [ID] [FLAC Lossless · 1521kbps].flac`
- 用户选择 FLAC 但发生回退：按实际成品标为 MP3，不在文件名中标为 FLAC。

源编码名称采用简洁、稳定的展示值，例如 `FLAC`、`AAC`、`Opus`。源码率取 yt-dlp 已选格式提供的 `abr` 或 `tbr` 并四舍五入到整数 `kbps`。如果源编码或码率不可用，仅省略未知部分；文件名至少保留 `[MP3 V0]` 或 `[FLAC Lossless]`，不出现 `NA`、`None` 或猜测值。

## 架构与数据流

`downloader.py` 继续作为 CLI 与 Web 的共享核心。`audio_format` 通过以下链路传递：

`main.py` 或 `app.py` → `download_tasks()` → `download_video()` → 音频格式探测与 yt-dlp 选项构建。

`media_type` 仍只表示 `video` 或 `audio`；不会把 FLAC 增加为第三种媒体类型。下载结果增加以下字段：

- `audio_format_requested`：用户请求的 `mp3` 或 `flac`。
- `audio_format_used`：实际输出的 `mp3` 或 `flac`。
- `audio_format_fallback`：是否由 FLAC 回退为 MP3。
- `source_acodec`：已选源音轨编码的规范化名称。
- `source_abr_kbps`：源音轨可用的近似码率。

Bilibili 下载本来就有一次只读元数据提取，直接复用其已选格式判断 FLAC。其他平台仅在用户请求 FLAC 时执行轻量元数据预检；默认 MP3 路径不增加额外请求。确定实际输出格式后再构建对应后处理链。

音频完成全部后处理后，根据实际格式与已选源信息生成质量标签并重命名最终文件。重命名逻辑必须使用现有输出路径作为输入，保留平台 ID 命名规则，并让返回结果、CLI 汇总和 Web 任务状态使用重命名后的真实路径。

## Web 与命令行入口

### Web

- 继续使用现有独立音频输入区，不新增第三个输入框。
- 音频区增加 `MP3 V0 / 源 FLAC` 切换，默认选中 MP3 V0。
- `/api/download` 新增字符串字段 `audio_format`，仅接受 `mp3` 或 `flac`；视频批次忽略其展示但仍使用安全默认值。
- 音频任务卡显示请求格式、实际格式、源编码和源码率。发生回退时显示明确的回退提示。
- 现有单活动批次、视频与音频输入互斥、最大并发和 Bilibili 极速模式行为不变。

### CLI

- `python main.py --audio URL...` 继续输出 MP3 V0。
- `python main.py --audio --flac URL...` 请求源 FLAC。
- 交互模式选择音频后，再选择 MP3 V0 或源 FLAC；默认仍为 MP3 V0。
- `--flac` 未与 `--audio` 一起使用时给出清晰用法提示，不静默改变视频下载类型。
- 汇总中显示实际输出格式；FLAC 回退时额外显示回退原因。

## 错误处理与边界

- 缩略图不存在时不报错，也不影响音频文件成功状态。
- 源站没有 FLAC 不属于任务失败，按已确认规则回退 MP3 V0。
- FLAC 音轨本身下载失败时沿用现有平台重试、Bilibili CDN 回退和任务隔离机制，不假装已经成功生成无损文件。
- 封面嵌入或音频转换发生真实 FFmpeg 错误时，沿用现有后处理失败逻辑并给出清晰错误。
- MP3 由 FLAC、AAC 或 Opus 转码后仍只标记为 MP3 V0；源编码信息仅说明输入来源，不声称成品无损。
- 不增加音频规格手工选择，不提供伪造采样率、位深或固定码率的选项。

## 测试与验收

- 单元测试覆盖 MP3 与 FLAC 后处理器、后处理顺序、缩略图下载配置和无缩略图跳过行为。
- 单元测试覆盖源编码规范化、码率标签、缺失字段、最终路径重命名和平台 ID 保留。
- 单元测试覆盖 FLAC 可用、FLAC 不可用时回退 MP3，以及新增结果字段。
- CLI 测试覆盖默认 MP3、`--audio --flac`、交互选择和无效 `--flac` 用法。
- Flask 与页面测试覆盖 `audio_format` 校验、格式切换、请求传递和回退状态展示。
- 对示例 `BV1fsTM6CE9P` 执行真实只读格式探测，必须选中 `30251 / FLAC`。
- 不在自动化验证中下载约 783 MB 的整张专辑；使用短片段验证实际 FLAC 编码、MP3/FLAC 内嵌封面和最终命名，并用 FFprobe 检查音频与封面流。
- 最终运行完整单元测试、`compileall`、`git diff --check`，并检查测试产物没有遗留独立缩略图。

## 非目标

- 不将 MP3 成品描述为 Hi-Res 或无损。
- 不把有损源转码为 FLAC。
- 不改变视频下载格式、视频命名或现有并发限制。
- 不下载整张示例专辑作为每次回归测试的一部分。
