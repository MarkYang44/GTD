# 并行下载与进度乱码修复设计

## 背景与目标

当前 `download_tasks()` 逐项串行执行任务，批量链接必须等待前一项结束后才能开始下一项。Web 页面还会直接显示 yt-dlp `_percent_str` 中携带的 ANSI 终端颜色控制码，导致百分比呈现为 `�[0;94m100.0%�[0m` 一类乱码。

本次改动需要在不改变现有链接识别、平台参数、Cookie 查找、输出目录及失败继续策略的前提下：

1. 让一批任务最多同时下载 3 项，超过上限的任务继续等待。
2. 保持结果列表与用户输入顺序一致。
3. 保证 Web 任务卡的状态与进度仍对应正确任务。
4. 清除进度百分比中的 ANSI 控制码。
5. 让 Web 与命令行入口复用同一套并行下载行为。

## 方案选择

采用 `concurrent.futures.ThreadPoolExecutor` 在核心下载层并发执行单项任务。

未采用以下方案：

- 仅在 `app.py` 创建多个下载线程：会导致 Web 与命令行行为不一致，并重复任务调度逻辑。
- 使用多进程：下载主要是网络与外部程序 I/O，多进程增加状态传递和进度回调复杂度，没有必要。

## 核心设计

### 并发入口

`download_tasks()` 保持现有函数签名和调用方式。核心模块新增值为 `3` 的 `MAX_PARALLEL_DOWNLOADS` 常量，函数使用该常量创建最多 3 个工作线程，并为每个任务提交一个独立下载工作单元。

每个工作单元执行以下流程：

1. 使用输入列表中的原始零基索引发送 `started` 事件。
2. 调用 `download_video()`，并将进度事件附加同一原始索引后转发。
3. 成功时发送 `completed`，失败时发送 `failed`。
4. 返回原任务与下载结果。

调度器按照任务索引写入预分配的结果槽位，最终仍返回 `list[tuple[VideoTask, Optional[DownloadResult]]]`，顺序与输入保持一致，而不是按完成时间排序。

### 并发上限

上限固定为 3，Web 和命令行入口无需额外配置即可使用。工作线程数取 `min(MAX_PARALLEL_DOWNLOADS, len(tasks))`；空任务列表直接返回空结果，不创建线程池。

本次不增加网页并发设置控件、配置文件或命令行参数，避免超出需求。

### 状态与线程安全

Web 状态继续由 `app.py` 的 `_lock` 保护。不同工作线程可以同时触发回调，但 `_on_progress()` 在持锁后才读取和修改批次状态。

`completed` 和 `failed` 计数只在对应终态首次到达时增加，避免重复终态事件造成计数超过任务总数。任务状态允许从 `pending` 进入 `downloading`，再进入 `completed` 或 `failed`。

`all_done` 仅在整个 `download_tasks()` 返回后设置，因此表示所有工作线程均已结束。

### Instagram 请求节流

删除原先批次串行循环中“每个 Instagram 任务之后等待 3 秒”的逻辑，因为并行执行后该等待无法控制其他已经启动的线程。

保留每个 Instagram yt-dlp 实例已有的 `sleep_interval`、`max_sleep_interval` 和 `sleep_interval_requests` 设置。最大并发限制为 3，用于兼顾吞吐量与平台限流风险。本次不实现跨线程的全局 Instagram 启动间隔。

### 进度文本清洗

在 `downloader.py` 的进度快照提取阶段清洗 `_percent_str`：

1. 将值转成字符串。
2. 使用 ANSI 转义序列正则删除 SGR 等终端控制序列。
3. 去除首尾空白。
4. 清洗后为空时显示“计算中”。

清洗发生在数据源边界，因此 Web 回调和命令行输出都会得到纯文本百分比。速度和 ETA 的现有格式保持不变。

### 命令行输出

并行任务不能共享单行回车刷新，否则多个线程会互相覆盖。下载进度输出改为完整行输出，并保留任务编号，使交错出现时仍能识别来源。完成、错误和最终汇总逻辑保持现状。

## 错误处理

- `download_video()` 已捕获 yt-dlp 下载错误与普通异常，并返回 `None`；工作线程据此发送失败事件。
- 为避免单个工作线程的意外异常中断整批调度，调度器在收集 Future 时将异常转换为该项失败结果，同时继续等待其他任务。
- Web 失败卡片仍展示现有通用“下载失败”信息。本次不扩展错误对象结构。
- 某项失败不会取消尚未开始或正在执行的任务。

## 测试设计

在不进行真实网络下载的单元测试中验证：

1. ANSI 彩色百分比清洗为纯 `100.0%`，普通百分比保持不变。
2. 同时运行的工作单元从不超过 3 个，并且确实能观察到两个以上任务并发。
3. 不同完成顺序下，返回结果仍与输入顺序一致。
4. 单项失败后其他项继续执行并返回结果。
5. `started`、`progress`、`completed`、`failed` 事件携带正确原始任务索引。
6. Web 批次在并发终态事件下正确累计成功和失败数，重复终态不重复计数。
7. 现有链接识别、平台下载参数、错误提示及 Web 进度测试全部通过。

## 验收标准

- 提交至少 4 个模拟下载任务时，最多 3 个任务可同时处于执行状态，剩余任务等待工作线程空闲。
- 任意任务完成或失败后，队列中的下一任务可以开始。
- 页面不再显示 `�[`、`[0;94m` 或其他 ANSI 片段，百分比显示为正常纯文本。
- 页面任务卡、完成/失败计数和最终结果与原始输入一一对应。
- 命令行与 Web 模式均使用默认并发数 3。
- 全部自动化测试通过，Python 文件可成功编译。

## 范围外事项

- 不增加暂停、取消、重试按钮。
- 不支持运行中修改并发数。
- 不引入持久化任务数据库。
- 不改变文件命名、覆盖策略、视频质量或 Cookie 规则。
- 不处理同一 URL 重复提交时的文件竞争；沿用 yt-dlp 当前行为。
