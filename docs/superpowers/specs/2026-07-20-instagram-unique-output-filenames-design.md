# Instagram 唯一输出文件名修复设计

## 背景与目标

Instagram 提取器可能为同一作者的多个不同视频返回相同标题，例如 `Video by same.author`。当前下载模板仅使用 `%(title)s.%(ext)s`，因此这些视频会映射到同一个输出路径。yt-dlp 随后可能把后续任务视为已有文件，或让并行任务竞争同一路径，导致一批指定链接最终只保留一个视频。

本次修复需要保证同一作者、标题相同但视频 ID 不同的 Instagram 链接生成不同文件路径并全部下载，同时保持现有 YouTube 文件名、CLI、Web、混合批次和并行下载行为不变。

## 方案选择

采用方案 A：仅为 Instagram 输出文件名追加视频 ID：

```text
%(title)s [%(id)s].%(ext)s
```

未采用以下方案：

- 所有平台统一追加 ID：虽然规则统一，但会无必要地改变现有 YouTube 文件名。
- 发生重名时追加批次序号：序号依赖输入顺序，跨批次无法稳定标识同一视频，且实现复杂度更高。

## 核心设计

`_build_ydl_options()` 继续先构建公共 yt-dlp 配置。YouTube 沿用当前的 `%(title)s.%(ext)s` 模板；进入 Instagram 配置分支时，将 `outtmpl` 覆盖为 `%(title)s [%(id)s].%(ext)s`。

Instagram 的 `id` 来自 yt-dlp 提取结果，代表具体帖子、Reel 或视频。相同作者的不同视频具有不同 ID，因此即使标题相同，也会生成不同路径。例如：

```text
Video by same.author [AAA111].mp4
Video by same.author [BBB222].mp4
```

输出路径解析仍调用同一个 yt-dlp 实例的 `prepare_filename(info)`，所以 `_resolve_output_path()` 会自动使用新模板定位后处理后的 MP4 文件，无需增加独立的重命名逻辑。

## 数据流与兼容性

输入 URL、平台识别、任务列表和并发调度都不去重，也不需要修改。修复只发生在 Instagram 任务构建 yt-dlp 输出选项时：

1. 每个用户指定链接仍生成一个独立任务。
2. 每个 Instagram 任务按其提取到的视频 ID 生成唯一文件路径。
3. yt-dlp 将不同视频写入不同文件。
4. CLI 和 Web 继续收到与原任务索引对应的结果。

已有下载文件不会被迁移或重命名。修复后的同一视频再次下载时，会稳定映射到相同的“标题 + ID”路径，由 yt-dlp 沿用既有的已下载文件处理行为。

## 错误处理

不新增错误分支。视频 ID 缺失时，yt-dlp 会按其输出模板规则生成文件名；受支持的 Instagram 单视频提取结果正常应包含 ID。下载异常、Cookie、限流及单项失败后继续批次的现有处理保持不变。

## 测试设计

先添加失败回归测试，再实施修复：

1. 构建 Instagram yt-dlp 选项，使用相同标题、不同 ID 的两份模拟信息调用 `prepare_filename()`，断言得到两个不同路径。
2. 断言两个 Instagram 路径分别包含对应 ID，证明唯一性来自视频本身而非随机值或批次序号。
3. 断言 YouTube 输出模板仍为原来的 `%(title)s.%(ext)s`，防止扩大文件名变更范围。
4. 运行现有完整单元测试和 Python 编译检查，确认并行调度、Web 状态、进度与错误提示不受影响。

## 验收标准

- 同一作者的两个 Instagram 视频即使标题相同，也生成两个不同的最终 MP4 路径。
- Instagram 文件名保留可读标题，并包含方括号包裹的视频 ID。
- 一批任务中的所有不同 Instagram 视频都能独立下载和汇总。
- YouTube 文件命名规则保持不变。
- 现有测试与新增回归测试全部通过，Python 文件可成功编译。

## 范围外事项

- 不修改下载质量、Cookie、并发数量、进度展示或失败重试策略。
- 不迁移或重命名 `downloads/` 中的已有文件。
- 不改变用户重复提交同一个视频 URL 时的既有行为。
- 不引入下载归档文件或新的持久化去重机制。
